# Cross-Industry Job Vocabulary Discovery & Taxonomy Audit
# Phase 6, Block 2 — Research & Repository Inspection Report

================================================================================
1. EXECUTIVE SUMMARY
================================================================================

This document establishes the foundational research and taxonomy framework for transitioning the Resume Intelligence Platform from its current deterministic matching baseline (Phase 5) to a cross-industry semantic intelligence engine (Phase 6).

Key Findings from Working Tree Audit:
1. Domain Monoculture: The platform’s existing configuration files (skill_configs.py, matching_roles.py, normalization_configs.py) are 100% hardcoded for Software Engineering and Data/ML. Out of 62 known skills, 4 canonical roles, 5 seniority keywords, 5 skill aliases, 4 degrees, and 4 academic field aliases, 0% cover non-tech domains such as Human Resources, Finance, Healthcare, Sales, Supply Chain, Manufacturing, or Customer Success.
2. Ingestion Asymmetry (False Negative Generator): In resume_service.py (lines 91-95), extracted skills not found in KNOWN_SKILLS are isolated into unknown_skills, while only skill_data["known"] is assigned to resume_data["skills"]. Because matching_service.py (line 28) inspects only resume_data.get("skills"), any non-tech skill on a resume is silently dropped from matching. Meanwhile, jd_parser.py (lines 758-815) extracts unknown capitalized tokens into jd["skills"]. Consequently, when an HR or Finance JD requires domain tools (e.g., Workday, Bloomberg), the candidate’s matching resume will register 0 matches and a 100% missing-skill deficit.
3. Flat Skill Reductionism: Modern hiring evaluates credentials, licenses, domain experience, tool proficiencies, action outcomes, and mandatory statutory requirements. The current platform reduces all qualifications to a flat list of lowercase string comparisons in skill_matcher.py.
4. Architectural Path Forward: Attempting to solve cross-industry support by expanding a monolithic hardcoded Python set is mathematically unviable. Phase 6 must introduce a hybrid layered architecture:
   - Layer 1: Pluggable domain taxonomies (namespaced canonical vocabularies).
   - Layer 2: Open-vocabulary candidate bridging (unblocking resume unknown skills).
   - Layer 3: Context-aware entity typing (distinguishing skills from credentials and noise).
   - Layer 4: Dense semantic embeddings with empirically calibrated similarity gates.
   - Layer 5: Dual-track hybrid scoring that preserves Phase 5 deterministic vetoes.

2.2 Extraction Pipelines: Resumes vs. JDs
-----------------------------------------
- Resume Skill Extraction (src/parsers/skills_parser.py: lines 318-381):
  1. Splits designated skills section text by line and delimiter (extract_skill_candidates splits commas, pipes, slashes, and conjunctions).
  2. Bullet glyphs (•, ‣, ●, -, *) are stripped via _BULLET_PREFIX_RE.
  3. Compound concepts (Data Structures and Algorithms) and acronyms (CI/CD) are protected with null-byte masking before delimiter splitting.
  4. Candidates are tested against regex patterns compiled strictly from KNOWN_SKILLS and SKILL_ALIASES (build_skill_patterns).
  5. Segregation: Matches go to known_skills; non-matches meeting length criteria (<= 60 chars, <= 6 words) go to unknown_skills.

- Service Pipeline Disconnect (src/services/resume_service.py: lines 91-95):
  skills = normalize_skills(skill_data["known"])
  unknown_skills = skill_data["unknown"]
  ...
  resume_data = {
      ...
      "skills": skills,                  # ONLY known skills!
      "unknown_skills": unknown_skills,  # Segregated
  }

  In src/services/matching_service.py (line 28):
  resume_skills = resume_data.get("skills") or []
  jd_skills = jd_data.get("skills") or []
  skill_match = match_skills(resume_skills, jd_skills)

  Verified Behavior: unknown_skills from resumes are completely invisible to match_skills().

- JD Skill Extraction (src/parsers/jd_parser.py: lines 678-815):
  1. Scans non-noise section text line-by-line.
  2. Extracts known_matches via skill_patterns.
  3. Extracts unknown_matches via capitalized title-case regex ([A-Z][A-Za-z0-9]*(?:[-.][A-Za-z0-9]+)*) filtered against UNKNOWN_SKILL_STOPWORDS.
  4. Combines both known and unknown matches into the output skills and skill_requirements.

  Consequence of Extraction Asymmetry:
  If an HR JD requires Workday and PeopleSoft:
  - JD parser extracts: jd["skills"] = ["Workday", "PeopleSoft"].
  - Candidate resume has: Workday, PeopleSoft.
  - Resume parser puts them into unknown_skills because they are not in KNOWN_SKILLS.
  - Resume service passes: resume_data["skills"] = [].
  - Deterministic matcher produces: matched = [], missing_required = ["Workday", "PeopleSoft"].
  - Candidate receives a score of 0.0 and verdict Underqualified, despite having every required qualification.

2.3 Matching and Scoring Behavior
---------------------------------
1. Skill Matching (src/matching/skill_matcher.py: lines 1-20): Strict set membership: if skill in resume_set. No fuzzy matching, no token-overlap matching, no semantic expansion.
2. Deterministic Scorer (src/matching/scorer.py: lines 23-113): Calculates score based on 2.0x required vs 1.0x optional weighting. Missing required skills act as a hard veto against Strong Match.
3. Role Matching (src/matching/role_matcher.py: lines 1-56): Normalizes roles by stripping words in SENIORITY_LEVELS and checking against CANONICAL_ROLES. If a role is not in the 4 known tech roles, status is "unknown". Unknown roles earn a flat 50.0 neutral points.
4. Project Matching (src/matching/project_matcher.py: lines 1-20): Performs lowercase substring check (skill.lower() in line.lower()) across project bullet descriptions for JD skills.

2.4 Representation of Extended Qualifications
---------------------------------------------
- Certifications & Licenses: Discarded. Issue issues_resume.md:R-015 records that CERTIFICATIONS and PUBLICATIONS sections are not parsed and have no schema representation.
- Skill-Specific Experience: Supported in schema (src/matching/experience_matcher.py: lines 16-53), but extraction is bound to SKILL_YOE_PATTERN and KNOWN_SKILLS.
- Responsibilities vs. Outcomes: JD responsibilities are captured as raw text blocks in sections, but never semantically matched against candidate experience bullet points.

4. PROPOSED TAXONOMY AND RELATIONSHIP RULES
================================================================================

4.1 Relationship Definitions & Policy Matrix
--------------------------------------------
1. EXACT_ALIAS (Weight: 1.0)
   - Definition: Orthographic, punctuation, or commercial naming variations of identical entities.
   - Required Skill Veto Policy: Satisfies requirement (no veto).
   - Examples: PostgreSQL <-> Postgres; ReactJS <-> React; Scikit-learn <-> sklearn.

2. ABBREVIATION (Weight: 1.0)
   - Definition: Standard industry acronym and its verbatim expansion.
   - Required Skill Veto Policy: Satisfies requirement (no veto).
   - Examples: AWS <-> Amazon Web Services; GAAP <-> Generally Accepted Accounting Principles; ATS <-> Applicant Tracking System.

3. CLOSE_EQUIVALENT (Weight: 0.80 - 0.90)
   - Definition: Competing products or platforms with identical conceptual paradigms and near-zero transition friction.
   - Required Skill Veto Policy: Does NOT clear hard veto by default without explicit JD rule.
   - Examples: GCP <-> AWS; Tableau <-> Power BI; HubSpot CRM <-> Salesforce; Jira <-> Asana.

4. RELATED (Weight: 0.20 - 0.30)
   - Definition: Technologies or skills operating in the same domain but with distinct architectures, syntaxes, or roles.
   - Required Skill Veto Policy: Does NOT clear veto. Awards soft partial credit only.
   - Examples: Docker <-> Kubernetes; Python <-> R; SQL <-> NoSQL; Medical Billing <-> Medical Coding.

5. BROADER_NARROWER (Weight: 0.50 - 0.70 Directional)
   - Definition: A parent discipline and its specialized sub-field (hierarchical taxonomy).
   - Required Skill Veto Policy: Narrower candidate satisfies broader JD; broader candidate does NOT satisfy narrower JD.
   - Examples: Narrower -> Broader: Deep Learning satisfies Machine Learning. Broader -> Narrower: Machine Learning does NOT satisfy Deep Learning.

6. AMBIGUOUS (Weight: 0.0 Unresolved)
   - Definition: Homonyms, shared acronyms, or terms whose meaning depends strictly on sentence or job context.
   - Required Skill Veto Policy: Must be disambiguated by section or sibling skills before scoring.
   - Examples: CPR (Cardiopulmonary Resuscitation in Healthcare vs. CPR in Real Estate); PCA (Principal Component Analysis in Data vs. Patient Care Assistant in Healthcare).

7. CREDENTIAL_RELATION (Separate Dimension)
   - Definition: Formal license or certification associated with a domain competency.
   - Required Skill Veto Policy: Holding credential does not prove hands-on tool skill; tool skill does not waive statutory license.
   - Examples: CPA <-> Financial Reporting; RN License <-> Patient Triage; PMP <-> Project Scheduling.

4.2 Mandatory Technical & Domain Distinctions
---------------------------------------------
1. SQL vs. NoSQL:
   - Taxonomy: RELATED (Shared parent: Databases).
   - Rationale: Relational SQL engines (PostgreSQL, MySQL, Oracle) enforce ACID transactions, fixed tabular schemas, and relational integrity via foreign keys. NoSQL engines (MongoDB, Cassandra, DynamoDB) prioritize horizontal partition scalability, eventual consistency, and document/key-value storage. A senior relational DBA cannot be assumed to possess distributed Cassandra tuning skills.
   - Scoring Policy: MongoDB applying to a PostgreSQL JD receives 0.25 partial database credit, but flags Missing required skill: PostgreSQL.

2. Machine Learning vs. Deep Learning:
   - Taxonomy: BROADER_NARROWER (Parent: Machine Learning, Child: Deep Learning).
   - Rationale: Deep learning is an advanced subset of machine learning.
   - Policy: Scenario A (JD requires ML; Candidate has Deep Learning): Valid. Score credit: 0.90. Scenario B (JD requires Deep Learning [PyTorch, Transformers]; Candidate has traditional ML [Scikit-learn, Random Forests]): Deficit. Score credit: 0.40 (Hard veto preserved).

3. AI vs. Generative AI:
   - Taxonomy: BROADER_NARROWER (Parent: Artificial Intelligence, Child: Generative AI).
   - Rationale: AI is an umbrella term covering classical heuristics, rule-based systems, and traditional predictive models. Generative AI specifically entails autoregressive foundational models, prompt engineering, fine-tuning (LoRA), RAG pipelines, and diffusion models. General "AI familiarity" does not qualify a candidate to deploy LLM inference infrastructure.

4. Docker vs. Kubernetes:
   - Taxonomy: RELATED (Shared domain: Containerization & Cloud Infrastructure).
   - Rationale: Docker is a container packaging runtime executing on a single operating system host. Kubernetes is a distributed cluster orchestration platform managing service discovery, ingress routing, auto-scaling, pod lifecycle, and persistent volumes across hundreds of nodes. Containerizing an application via a Dockerfile does not demonstrate cluster administration competency.
   - Policy: Docker earns 0.30 related container credit against Kubernetes, but cannot satisfy missing_required: Kubernetes.

5. HRIS vs. ATS:
   - Taxonomy: RELATED (Shared domain: HR Technology).
   - Rationale: An ATS (Greenhouse, Lever) manages candidate application stages, resume parsing, interview scheduling, and offer letters (pre-hire). An HRIS (Workday, ADP) manages employee payroll, benefits, organizational hierarchy, PTO tracking, and compliance filings (post-hire). Operating an ATS does not qualify an HR coordinator to manage multi-state payroll deductions.

6. Financial Reporting vs. Financial Forecasting:
   - Taxonomy: RELATED (Shared parent: Corporate Finance).
   - Rationale: Financial reporting is backward-looking, governance-focused, and governed by strict legal standards (GAAP, IFRS, SEC filings) to record actual accounting results. Financial forecasting (FP&A) is forward-looking, probabilistic, and modeling-focused, simulating future revenue scenarios based on market assumptions.

7. Project Coordination vs. Project Management:
   - Taxonomy: BROADER_NARROWER / SENIORITY_GRADIENT.
   - Rationale: Project coordinators manage administrative scheduling, meeting agendas, minutes, and document collation under supervision. Project managers own end-to-end accountability for project budgets, critical path scheduling, scope negotiation, resource allocation, and executive escalation. Treating them as identical produces severe underqualification false positives.

8. Professional Certification vs. Practical Proficiency:
   - Taxonomy: CREDENTIAL_RELATION.
   - Rationale: A software engineer with 8 years of production AWS architecture experience may not hold the AWS Solutions Architect certificate, yet should receive full credit for cloud architecture. In regulated industries (Healthcare, Accounting, Legal), a candidate with 10 years of nursing assistance experience cannot practice as a Registered Nurse without an active state RN License. Here, the credential is a non-negotiable statutory knockout.

5. CRITICAL FALSE-POSITIVE AND FALSE-NEGATIVE RISKS
================================================================================

5.1 High-Impact False-Positive Risks
------------------------------------
1. Substring & Word Boundary Collisions: Java appearing as a substring inside JavaScript. Boundary regex (?<!\w)Java(?!\w) in skills_parser.py prevents raw regex overlap, but semantic embedding layers frequently place Java and JavaScript close (cosine similarity ~0.78) due to shared programming contexts.
2. Unanchored Embedding Similarity Drift: In pure vector-space matching, generic tools in the same job family often produce high cosine similarities (e.g., Excel and Python in data science; R and SQL). Without exact-match gates, a candidate proficient in Excel could erroneously satisfy a Python programming requirement.
3. Statutory & Regulatory Licensure Overrides: If a semantic matcher equates Medical Assistant with Physician Assistant because both work in clinic settings, the platform would recommend an unlicensed candidate for a role requiring medical prescription authority, creating severe liability.
4. Soft-Skill & Verb Extraction Noise: Extracting capitalized narrative verbs (Lead, Analyze, Execute, Drive, Support) as technical skills artificially inflates candidate match percentages while ignoring true core competencies.

5.2 High-Impact False-Negative Risks
------------------------------------
1. Acronym & Abbreviation Disconnect: A candidate writing K8s rejected against a JD requiring Kubernetes. A nurse writing BLS, ACLS rejected against a hospital JD requiring Basic Life Support. An accountant listing GAAP rejected against a JD requiring Generally Accepted Accounting Principles.
2. Delimiter & Compound Term Fragmentation: Technical concepts containing slashes or conjunctions (TCP/IP, ETL/ELT, P&L, AP/AR, Research and Development) being fractured into individual meaningless fragments (AP, AR) when parsed by generic delimiter splitters.
3. Resume Unknown Skill Discard: Candidates in HR, Healthcare, Finance, or Logistics currently have 100% of their specialized tools (Cerner, NetSuite, WMS, Epic) diverted into unknown_skills and omitted from matching.


================================================================================
6. MISSING REQUIREMENT CATEGORIES BEYOND ORDINARY SKILLS
================================================================================

1. Obligation Context (Required vs. Preferred): Phase 5 established required (2.0x) vs. optional (1.0x) scoring in scorer.py. However, this must be extended beyond skills to education, years of experience, and certifications.
2. Tenure Specifications (Minimum vs. Preferred YOE): Real JDs frequently specify: "Minimum 3 years of experience required; 5+ years preferred." Flattening this to 36 or 60 months either unfairly penalizes qualified candidates or fails to reward exceptional candidates.
3. Domain & Industry Track: 5 years of software engineering in high-frequency trading (HFT) requires ultra-low-latency C++ knowledge that cannot be substituted by 5 years of C++ in embedded automotive systems. Domain context must qualify the skill.
4. Statutory Credentials & State Licenses: In healthcare, accounting, law, and civil engineering, licenses (RN, CPA, PE, Bar Admission) are binary prerequisites. A candidate lacking a required license must receive an immediate knockout veto regardless of skill match.
5. Educational Pedigree & Minimum Degree Level: The platform extracts degrees in education_parser.py, but does not verify whether the candidate meets the minimum required level (e.g. Master's degree required for a Data Science Research Scientist).
6. Responsibilities & Outcome Verifications: Senior roles require demonstrated achievements: "Scaled engineering team from 5 to 30", "Managed $10M annual marketing spend at < $25 CAC". Flat skill matching cannot evaluate scope or performance.
7. Seniority & Organizational Scope: Headcount responsibility, direct reports, P&L ownership, and cross-functional governance must be distinguished from individual contributor task execution.
8. Tool Familiarity vs. Conceptual Architecture: Knowing how to call a REST API vs. knowing how to design and architect distributed, resilient API infrastructure.
9. Mandatory Statutory Conditions (Knockout Criteria): Security clearance (TS/SCI), legal work authorization without sponsorship, physical requirements (ability to lift 50 lbs in warehousing), or active driver's license.

8. RECOMMENDED PHASE 6 ARCHITECTURE AND TRADE-OFFS
================================================================================

8.1 Limits of Hardcoded Monoliths
---------------------------------
English business and technical vocabulary spans hundreds of thousands of specialized terms, tools, certifications, and variants. Hardcoding every skill in Python sets creates an unmaintainable codebase prone to human error, spelling regressions, and immediate staleness. However, relying entirely on unconstrained ML embeddings introduces dangerous false positives (e.g. confusing Java and JavaScript, or conflating distinct nursing licenses).

8.2 Recommended 4-Tier Hybrid Architecture
------------------------------------------
- Tier 1: Deterministic Core
  * Exact Match & Canonical Alias Normalization (Confidence: 1.0).
  * Fast string lookup; covers 70-80% of standard mentions.
- Tier 2: Domain Taxonomy Packs (Namespaced)
  * Pluggable JSON/YAML configurations by industry (Tech, Finance, Health, HR).
  * Bidirectional abbreviations (AWS <-> Amazon Web Services, CPA <-> Certified Public Accountant).
  * Protects compound phrases from delimiter fragmentation.
- Tier 3: Dense Semantic Embeddings & Calibrated Gates
  * Local, lightweight Sentence-Transformers (e.g. all-MiniLM-L6-v2) or ONNX runtime.
  * Evaluates unmapped terms against JD requirements.
  * Cosine similarity threshold dynamically gated by relationship taxonomy.
- Tier 4: Contextual Requirement & Audit Layer
  * Distinguishes tools vs. licenses vs. responsibilities.
  * Enforces hard requirement vetoes (semantic similarity cannot bypass veto).
  * Surfaces complete transparent explainability trail to human recruiters.

8.3 Pitfall of Universal Thresholds (e.g. 0.82)
-----------------------------------------------
A similarity threshold cannot be treated as a universal physical constant.
In embedding spaces (such as all-MiniLM-L6-v2), cosine similarity distributions vary drastically by entity type:
- Short acronyms vs. expansions (AWS vs. Amazon Web Services): Often score between 0.88 and 0.95.
- Competing products (AWS vs. GCP, Tableau vs. Power BI): Frequently score between 0.78 and 0.85 (high risk of false positive equivalence if threshold is set at 0.80).
- Sentence-level project bullets vs. JD responsibilities: Typically score between 0.65 and 0.78 due to varied prose structure.
Policy Decision: Thresholds must be calibrated per relationship category against an empirical labeled evaluation set, with strict exclusion rules for related-but-non-equivalent entities.

11. OPEN QUESTIONS REQUIRING HUMAN DECISIONS
================================================================================

1. Job Family Detection Strategy:
   - Question: Should the active job family (e.g. Healthcare vs. Software vs. Finance) be automatically inferred from JD section text, or explicitly specified via an API parameter / recruiter dropdown?
   - Trade-off: Automatic detection can misclassify hybrid roles (e.g. Healthcare Data Analyst, FinTech Backend Engineer); explicit parameters require UI inputs.

2. Statutory License Knockout Policy:
   - Question: Should missing statutory credentials (e.g., lack of active RN License for an Intensive Care Nurse position) result in an immediate composite score of 0.0 (hard knockout), or simply cap the candidate at Underqualified with flags?
   - Trade-off: Hard knockout prevents illegal hiring recommendations in regulated industries; soft cap allows recruiter discretion for trainees or transfer candidates.

3. Equivalence Weight Policy for Competing Platforms:
   - Question: In non-regulated roles, how should competing tools be credited (e.g., candidate has Tableau, JD requires Power BI; candidate has GCP, JD requires AWS)?
   - Recommendation for Review: Should competing tools earn partial credit (e.g. 0.80) or zero credit if marked required?

4. Offline Inference vs. Model Dependencies:
   - Question: Is adding sentence-transformers (~80MB download + PyTorch/ONNX runtime) acceptable in the production deployment environment, or should the platform support a pure rule/taxonomy mode for resource-constrained environments?
   - Trade-off: Embedding models add ~15ms CPU inference and ~200MB memory overhead; rule-based taxonomy mode uses < 10MB memory and < 1ms execution, but requires ongoing manual dictionary maintenance.
